# Inter-module dependency map (Department Dashboard)

Apps Script gives a project **one global scope**: every `.gs` file's top-level
functions and constants are visible to every other file, and there are no
`import` statements to read. The dependency graph a normal codebase wears on
its sleeve is therefore invisible here — the only way to know that `Util.gs` is
reachable from almost every other file (the exact count is in the generated
table below) is to compute it.

That number is the difference between *a local edit* and *a whole-project
change*, which is why this file exists. Produced by
[`scripts/module-deps.mjs`](../scripts/module-deps.mjs); see
[`architecture.md`](architecture.md) for the data flow this graph sits under.

**Refresh it** after adding, removing, or renaming a `.gs` file, or after
moving a shared helper:

```bash
node scripts/module-deps.mjs --write     # regenerate the tables below
node scripts/module-deps.mjs --check     # exit 1 if they are stale
node scripts/module-deps.mjs             # print, write nothing
```

`--check` **runs in CI** (the `test` job, T-3): a new or renamed `.gs` file
fails the build until the tables are regenerated, which is one `--write` away.
(DOC-5: this said "not in CI" after T-3 had put it there. The prose above the
generated block quotes no counts, since only the table is kept current.)

## How to read it

`Depended on by` counts the OTHER files referencing a symbol this file defines.
It is the **blast radius**: the five foundation modules below are reached by
most of the project (the generated table has today's shares), so nothing in them is a local change.

Method and its limits, so the numbers are not over-trusted:

- **Definitions** are top-level `function NAME(` plus top-level `SCREAMING_CASE`
  const/var/let. Nested helpers are not indexed — they are not cross-file
  reachable anyway.
- **References** are word-boundary matches in another file, **after comments
  are stripped**. This matters here: the comments are unusually dense and name
  symbols constantly, and counting them inflated `Config.gs` by 4 files and
  `Setup.gs` by 9.
- It is still a **heuristic, not a parse**. A symbol named inside a string
  literal (a `Pipeline Health` step name, say) is counted. Read the figures as
  magnitudes, not exact call counts.
- Scope is the dashboard's `.gs` files only. The 11-fragment client
  (`script-N-*.html`) shares one IIFE scope and is not analyzed here; see
  [`client-ui-conventions.md`](client-ui-conventions.md).

Two shapes worth naming:

- **`SystemHealth.gs` is the inverse of the foundation** — almost nothing
  depends on it, and it depends on almost everything. That is correct for an
  aggregator, and it means Health breaks *because* something else changed,
  never the reverse.
- **`Data.gs` is the widest single file (111 KB)** and sits directly under four
  dependencies while feeding every report. It is the highest-leverage file in
  the project in both directions.

## Cross-project seams

These are not in the tables — they cross Apps Script project boundaries, where
the shared global scope does not reach and no fan-out count applies. Each is a
place where two files must agree and nothing structural forces them to.

```
cdr-import  ══ BYTE-IDENTICAL ══  cdr-report
    neonWrite.js · buildDQEHistoricalData.js               INV-16  guard ✅
    sanitizeAbandonedCellForNeon_ / sanitizeSlotCellForNeon_        guard ✅
    simulateSplitCol2 / parseDurationDecimal (CODE-compare)         guard ✅

cdr-import  ─── hashPhone ≟ cdrHashPhone_ ───  cdr-report
    DIFFERENT projects, so the INV-16 guard cannot pair them.
    Divergence is SILENT: nothing joins, every insurer renders
    "(unlabeled)", no error and no count gap.        insurance-numbers.test.js ✅

pipeline    ───reads roster───▶  dashboard sheets   INV-24 / INV-46
dashboard   ───writes aliases, renameAgentInNeon_──▶  pipeline / Neon
dashboard   ─── DASHBOARD_WORK_WINDOW mirrors pipeline constants ──▶  INV-06 ✅
                4 copies, all derived from the pipeline in cross-file-pins
```

Four **hand-mirrored rule sets** re-implement pipeline logic in structurally
different code, so no diff can compare them; three are pinned behaviourally:

| Mirror | Pinned by |
|---|---|
| `dataFilters.js` Extraction Sidebar ↔ `autoImport.js` QCD rules | `qcd-sidebar-parity.test.js` (cols F/G excluded — a MAX and a MEAN) |
| `DQEdrilldown.js` ↔ the DQE build | `dqe-drilldown-parity.test.js` — **has drifted three times** |
| `NeonMirror.js` sanitizers ↔ `neonbackfill.js` | `check-duplicated-files.sh` |
| `DASHBOARD_WORK_WINDOW` + `INBOUND_WORK_WINDOW_PST` + `DQE_DD_WINDOW_*` ↔ pipeline window | `cross-file-pins.test.js` (S1/INV-06) — every mirror derived from `DQE_WINDOW_START/END` |
